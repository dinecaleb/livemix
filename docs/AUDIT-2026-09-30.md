# DINE broadcast-readiness audit — 2026-09-30

The question asked: would you trust DINE to run a three-hour live broadcast in front of thousands? This is what
the code does, traced end to end (six parallel read-only audits, every P0/P1 re-checked by hand), what was fixed
today, and what is left. Nothing here is from filenames or UI; each claim has a file and a line in the commit
that fixed it or in the section below.

**Verdict, before today: no.** Four P0s could take a service down or lose it silently (a use-after-free on the
audio thread, crash recovery that recovered nothing, a take recording into nothing, Autopilot with no working
feedback), and Mix Buddy could change what the room heard from a sentence and KEEP a pending proposal nobody
had approved. **After today: the P0s are fixed and tested; the remaining P1s below are what stands between
DINE and an unattended service.** The one I would still not ship without a rig rehearsal is device identity
(inputs by index + device name).

---

## A. Architecture map (the real signal path)

```
CoreAudio callback  AudioHost.cpp:331  (ScopedNoDenormals; silence if not prepared)
 └ DawEngine::processBlock
    ├ RECORDER TAP: raw device inputs, before anything else (Recorder::write, lock-free FIFO -> writer thread)
    ├ input peak meters
    └ input matrix (device channel, or tape / silence per track)
 └ MixEngine::process   (parameter mailbox = TripleBuffer; sub-blocks of maxBlock)
    STRIP  inputA/B -> digital preamp (inputGainDb) -> [tap] -> ChannelProcessor:
             input meter -> trim x polarity -> [sample DETECT] -> HPF/LPF -> gate -> [sample SUM]
             -> corrective EQ -> de-esser -> comp -> transient -> tone EQ -> saturation -> width
             -> output trim -> output meter
           -> NaN guard (new) -> fader x pan (-3 dB sin/cos) -> group bus
           -> FX sends: post-fader, post-pan;   solo -> monitor bus (PFL unity / AFL at fader)
    GROUP  [tap] -> full ChannelProcessor -> NaN guard (new) -> solo -> monitor
           -> group fader x speech duck (DRUMS/BASS/MUSIC only) -> master sum
    FX     wet-only chain -> NaN guard (new) -> return gain -> master sum (not through any group)
    MASTER fader (before the chain) -> ChannelProcessor + lookahead limiter (1.5 ms, 4x true peak)
           + loudness meter -> NaN guard (new)
    MONITOR follows master when nothing soloed; own level, dim, mute
    FEEDS  monitor | master (post-limiter) | a group (post-chain, pre-master, unlimited)
           x feed gain (-60..+12) x DIM/MUTE ramp, summed onto device pairs
           -> OUTPUT GUARD (new): never more than full scale, never NaN
```

Reported latency: the master limiter's 72 samples at 48 kHz, constant. Group feeds and solo are 1.5 ms ahead of
the master feed (not compensated; P3). Everything analytic (listen, planner, Tune Live, Autopilot, Mix Buddy)
runs off the audio thread. Neither `MixEngine::process` nor `ChannelProcessor::process` allocates or locks.

Three decision systems sit above it, each with one job (now enforced, see G and Mix Buddy):
**TUNE MIX** (`MixPlanner` + `src/Tune` strategies, numbers from `src/Profiles`) proposes; **Autopilot**
(`src/Mix/Autopilot` + `MixController::pollAutopilot`) holds; **Mix Buddy** (`src/MixAI/MixBuddy`) explains.

## B. What already works (verified)

- Audio-thread discipline: TripleBuffer hand-off, no allocation or locks in the process path, denormals handled,
  RTSan wired in CI (`scripts/rtsan.sh`).
- Constant, honestly reported latency; 4x-oversampled true-peak limiter; BS.1770 metering.
- Solo never reaches the room in MONITOR mode; speech priority applied after the monitor's copy.
- Tune is deterministic and idempotent — confirmed today on the QUEENSVIEW service at two windows
  (`NO CHANGE REQUIRED`, -2.0 dBTP).
- Source-health basics: silence, faint, low (with the preamp move), DC, clicks-vs-clipping; a listen with no
  performance is refused.
- Sample replacement: detection before the filters, summed after the gate, missing bank = bit-identical pass-through.
- Session: one owned model, versioned store with migration, atomic writes, autosave on a worker, crash marker.
- Recorder: raw-input tap, header + sidecar kept current, crash repair on next open.
- Offline: telemetry, the OpenAI provider and TUNE LIVE all run on their own threads with timeouts; nothing
  network-related blocks startup or audio.

## D. Professional mixing gaps (open)

1. **Speech priority is a raw peak gate** (Speech bus pre-fader, -38 dBFS, 250 ms hold, no hysteresis). Stage bleed
   into an open lectern mic ducks the band during worship; a pad breathes between the pastor's phrases. Needs a
   slower, voice-weighted detector with open/close hysteresis and a longer hold (P1 for a service that uses it).
2. **Group balance uses whole-listen RMS for groups and active RMS for strips**, so a lead who sings half the
   listen reads 3 dB low and the band is pulled down (`MixPlanner.cpp:1196`). Correct fix is `activeRmsDb` or
   gated loudness for the bus — changes every mix's numbers, so it wants a QUEENSVIEW listen first (P1).
3. **Level prediction ignores EQ/HPF moves** (`predictedProcessed*`): the first TUNE mis-lands by 2-4 dB on
   shaped sources and RE-TUNE chases it (P2).
4. **Masking is narrow**: kick-vs-bass sub and one static 2.8 kHz pocket on keys/guitars. Cymbals/overheads vs
   vocal, BGV vs lead, horns, keys vs guitars are never carved; the pocket can land in the same octave as a
   guitar's definition boost, breaking the boost/cut invariant (P2).
5. **Context**: hierarchy changes for speech, but not for an instrumental solo or a choir-led moment; the
   AMBIENCE group is never ridden (P2). Autopilot now *holds still* on an arrangement change rather than
   mis-correcting — the conservative answer, not the complete one.
6. **HPF cap uses the strongest low peak, not the lowest note** (bass low E can be cut) (P2).
7. **Electric-guitar expander (30 dB range)** chops delay tails; auto-enabling kick samples at 100 % blend and
   gating toms harder is aggressive for a first TUNE and contradicts `DRUM-SAMPLE-REPLACEMENT-SCOPE.md` (P2,
   product decision).
8. **Master loudness fit has no limiter-GR bound** (RAISE LOUDNESS has one); a high-crest mix can ask the limiter
   for 6+ dB (P2).
9. Translation: mono below 100 Hz on the master and correlation-driven width exist; there is no mono-sum or
   phone-speaker check (P3).

## E. Reliability gaps (open)

1. **Device identity** — inputs are raw channel indices on a device matched by *name*; a returning device is
   trusted by name only, channel count and rate unchecked, while the toast says "every input is on the channel it
   was on". Two identical interfaces cannot be told apart. `DevicePlan` falls back to `outputs[0]` (possibly the
   PA or laptop speakers) with only a toast. Store CoreAudio UIDs and verify channel count on return (P1).
2. **Recorder FIFO**: 2.7 s per track; on overflow one writer drops a block while others don't (tracks misalign),
   drops aren't counted, and the take is ended. Bigger FIFO + counted, aligned drops (P1).
3. **Clip detection reads after DINE's digital gain**, so a converter still clipping after a -6 dB digital trim
   reads "Healthy" (and a +6 dB trim reads CLIP on a clean input). Meter before the preamp stage (P1).
4. Sample replacement lands 2.5-5 ms late and ALIGN only delays further (combing at partial blend); no hat-in-snare
   veto; kit veto depends on strip order (P1/P2).
5. **BYPASS still puts 20 raw inputs at unity with no master limiter on air** (the output guard now caps at full
   scale). Consider making BYPASS monitor-only, or LIVE SAFE-locked by default (P1, product decision).
6. Solo-in-place is restored from a saved session (P2); undo is memory-only (P3, history covers it); a routing
   change cuts audio and a running take without a fade (P2); `TimelinePlayer` buffers are 2x the prepared block
   (P2); wait loops free buffers after 2 s even if the audio thread still holds them (P2).
7. Hum, feedback, polarity between related mics, a single mis-patched input: not detected (P2).

## F. TUNE MIX assessment

It is a real mix planner, not a preset box: a 30-second listen measured per strip, per group and at the master,
a focal source, per-source targets from profile data, hierarchy rules (mix follows the lead, several leads summed,
BGV under lead, groups set against the lead), two masking rules, a delivery-loudness master fit, and bounded,
idempotent re-tunes. Selective application exists in the controller (strips and groups) but the UI exposes only
group chips — no per-strip or per-change accept; "PUT BACK" returns a stage to what TUNE set, not to before.
Missing: the items in D, a per-change accept/reject, and convergence on a *fresh* listen (only same-listen
idempotency is asserted).

## G. Autopilot assessment

Before: not a conservative assistant — no feedback, 300 ms snapshot target, chased song sections, fought the
engineer. **Now:** measures where each group lands (meter + fader) against the groups summed; learns over 8 s of
audio; decides on a 6 s average, at most one 0.5 dB step per 400 ms of audio, and credits its own moves at once
(converges instead of overshooting — the closed-loop test corrects a 6 dB step by 3 dB and stops inside
tolerance); holds still while the arrangement differs, on a frozen meter and during solo-in-place; any hand
move re-learns; a touched group is released; every move reaches the Mix history. Still missing by design: it
does not ride the room, react to harshness or to a newly active mic — it holds, it does not mix.

## H. DSP assessment

Biquads clamp frequency (10 Hz..0.49 fs) and Q (0.05..40); gain and compressor makeup were unclamped — now
bounded by `sanitizeChannelParameters` at every entry. EQ/filter/comp/gate switch on and off without a crossfade
and EQ coefficients update per block (clicks, zipper on fast moves; P2). Limiter is correct and honestly
reported. PFL (unity) vs AFL (-3 dB centre) levels differ (P3). Group mute does not mute that group's effect
sends (P2). Master fader sits before the master compressor (moving it changes compression; P3, by design).

## I. Performance assessment

Engine timing test: 64 strips inside a 64-sample callback passes. Benchmark: 48 channel instances at 256 samples
≈ 14 % of budget; sample stage adds ~1.2 %. The new NaN guard is one multiply-add per sample per stage — below
measurement. Every publish copies the full `MixParameters` onto the audio thread and re-runs `setParameters` on
every strip (no allocation, but CPU spikes during fader drags; P2). No soak test runs in ctest (P2).

## J. Persistence / recovery assessment

Everything that makes the mix is in `SessionState` except Autopilot (deliberate) and BYPASS/DIM/MUTE (deliberate).
Autosave is atomic and on a worker; recovery now survives until answered; a failed quit-save keeps the autosave;
corrupt values are clamped on load. Remaining: no fallback to the autosave when the main document is corrupt, a
newer-version file is not refused (fields silently dropped), autosave has no maximum wait under continuous change,
no BWF timestamp on takes (P2/P3).

## K. Recommended changes

- **P0** — none open.
- **P1** — device identity by UID + channel-count check on return (E1); recorder FIFO + aligned counted drops (E2);
  pre-preamp clip metering (E3); speech-priority detector (D1); group balance on active loudness, verified on
  QUEENSVIEW (D2); BYPASS off the air or LIVE SAFE-locked (E5); sample timing (E4).
- **P2** — level prediction with EQ; wider masking + honour the boost/cut invariant in the pocket; per-strip /
  per-change KEEP in the UI; master fit limiter-GR bound; stage crossfades; group mute on sends; soak test in CI;
  hum / feedback / polarity detection; solo-in-place not restored; smaller publish cost.
- **P3** — delay-compensate feeds; PFL/AFL level match; mono/phone translation check; BWF timestamps.

## L. Tests added today

`SampleLibrary: a reload never frees or rewrites what the engine was given` · `Autosave: the work offered back
survives everything that happens before the answer` · `MixEngine: a stage that stops producing numbers drops out
for a block` · `MixEngine: the device is never handed more than full scale` · `SessionStore: a corrupt file is
held inside what a knob can reach` · `SessionStore: the engineer's listen comes back on the master from a file
with fewer groups` · output-feed collision cases · BYPASS keeps MUTE · `Autopilot: a different arrangement is not
a drift` · `Autopilot: a reading that is not a number moves nothing` · `Autopilot, closed loop through the engine`
· five `Mix Buddy:` engine tests · `Mix Buddy: a question never changes the mix, and nothing is kept for you` ·
`Recorder: a take that stops reaching the disk is found and said` · `DawEngine: a take is one sample rate` ·
`MixController: a mix is never handed to an engine playing a different set of inputs`.

**Mix-quality benchmark:** `dine_mix_stems` already renders raw/before/after/re-tuned with LUFS, true peak, crest,
band balance and correlation, but only asserts idempotency. Next step: a `--check` mode asserting true peak ≤
ceiling, integrated LUFS within ±1 LU of target, no band more than N dB from the profile, correlation > 0.3, and a
fresh-listen convergence bound, run over QUEENSVIEW windows plus a speech-only and an acoustic multitrack (none
exists yet in the repo). Listening remains necessary for vocal intelligibility, masking and depth.

**Left open, with the reason:**

- **Hum / feedback / polarity detection.** The analysis keeps a third-octave spectrum of the whole listen, which
  cannot tell 60 Hz hum from a kick's fundamental or a held bass note; a detector that is right needs the spectrum
  of the quiet frames and cross-channel correlation for polarity. New analysis, not a fix.
- **Wider masking** (cymbals vs vocal, BGV vs lead, horns). New decision rules that need listening tests.
- **EQ-aware level prediction.** Still ignores EQ; after the calibration TUNE converges to within 1-4 dB of group
  movement, so this is now a refinement.
- **TUNE switching samples on by itself** (toms especially) and **SOLO IN PLACE / BYPASS policy** beyond what is
  above: product decisions, not defects.
- **Feed delay compensation** (group feeds 1.5 ms ahead of the master feed): below anything audible in a
  broadcast; left alone rather than adding latency to the listen.
