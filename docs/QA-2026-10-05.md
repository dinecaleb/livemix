# DINE reliability pass, 2026-10-05: five things found in real use

Each section gives the root cause, as traced, and what changed. The regression tests are in
`app/Tests/ReliabilityPassTests.cpp` (`dine_app_tests`) and in the `Undo:` cases of
`app/Tests/ReachabilityTests.cpp` (`dine_ui_tests`).

## 1. "DINE asks for the microphone again, and then cannot read Dante / the interface"

**Classification: B (signing), C (device error and permission confused) and D (ordering), together.**
`MicPermission` itself is correct: `check()` never prompts, and `request()` only prompts when the state is
Undetermined.

- **B, signing.** A Ninja build ignores JUCE's Xcode-only signing attributes. `DINE.app` therefore carries the
  linker's ad-hoc signature, whose designated requirement is `cdhash H"..."`, and that hash changes on every
  build. macOS keys the microphone answer to that requirement, so every rebuild is a new app to macOS and the
  question comes back. The default `scripts/package.sh` (no `DEVELOPER_ID`) is also ad-hoc, so every new zip
  a tester installs is a new app too. The bundle id also changed in the DINE rename, from `com.dine.dlive` to
  `com.dine.app`, so every grant made before 2026-10-01 was lost once.
- **C, device error and permission confused.**
  - `AudioHost::open` worded a real CoreAudio failure as "macOS is not letting it hear the inputs" whenever
    macOS also said Denied, and ignored the device's own error. Examples of real failures: no shared sample
    rate between Dante Virtual Soundcard and the speakers, a busy device, Dante not running.
  - In the other direction, with Denied, the input was still opened. CoreAudio hands a refused app an input
    that opens and stays silent. DINE then showed "running, 64 in" over still meters, which is the
    "cannot read Dante" symptom.
- **D, ordering.**
  - A recovery, opening from the library, and a hot-plug reopen opened the input without DINE's explanation,
    so macOS's bare prompt appeared under the recovery sheet.
  - Both permission callbacks ignored the answer.
  - Nothing noticed a grant made later in System Settings.
  - A console that appeared after launch was never opened. This includes Dante Virtual Soundcard, which
    often starts after login.

**Changed:**

- **One rule, decided before any device is touched:** `inputAccessFor` in `DeviceState.h`. `AudioHost::open`
  opens the input only when macOS says Granted.
  - Undetermined opens the output on its own and says nothing is being heard yet.
  - Denied and Restricted open the output on its own, each with its own sentence. The input is not even
    tried, so it is never opened silent.
  - A device error is only ever reported after the input was tried, in the device's own words.
- **Output-only fallback kept.** A missing input is never "no audio device".
- `MainView::followMicrophone` runs on the slow tick:
  - It opens the held input the moment macOS says yes, whether the prompt was just answered or the switch was
    turned on in System Settings while DINE was running. No relaunch is needed.
  - Once per run, when a session opened without asking, it shows the existing explanation sheet and then the
    prompt.
  - Neither happens mid-take or under LIVE SAFE.
- `HostServices::openWantedConsoleIfBack` opens the session's own console when it appears after the session
  opened on a stand-in. It only does this while standing in, never mid-take, and never under LIVE SAFE.
- The crash sidecar now records the take's device channels (see section 2).
- **Signing.**
  - `DINE_SIGN_IDENTITY` (`app/CMakeLists.txt`) signs the bundle after the samples are copied in.
  - `scripts/dine.sh` picks the first "Apple Development" identity on its own. `DINE_SIGN_IDENTITY=-` keeps
    ad-hoc.
  - The designated requirement becomes `identifier "com.dine.app" and anchor apple generic and certificate
    leaf[...]`. It is stable across builds, as verified with `codesign -d -r-` on this Mac.
  - `scripts/package.sh` takes `SIGN_ID` for the same reason, and its ad-hoc path now says that macOS will ask
    again.

**Build modes:**

| Build | Before | After |
| --- | --- | --- |
| Dev build, ad-hoc | Asked again after every rebuild | Unchanged when no identity is present; a note is printed |
| Dev build, `dine.sh` with an Apple Development identity | — | Stable identity: asked once |
| `package.sh`, ad-hoc | Asked again after every new zip | Unchanged; a note is printed |
| `package.sh`, `SIGN_ID` | — | Stable across zips |
| `package.sh`, `DEVELOPER_ID` + notarized | Stable | Stable |

The Developer ID build was **not** tested: this Mac has no "Developer ID Application" certificate, only Apple
Development and Apple Distribution. The prompt itself was not exercised either, because DINE was not launched
in this pass (see the notes on the user's own running instance).

## 2. A stereo input recorded as one channel

**Root cause.**

- `AssignPage::commit()` (`app/ui/SetupPages.cpp`) gave the new assignments to `MixController` and to nothing
  else. `DawEngine` keeps its own copy of the session, which the recorder reads. That copy only moved on a
  `reconfigure()`: CONTINUE called it, the sidebar did not.
- So a pair linked mid-session showed as one stereo strip on the mixer, while `DawEngine::startRecording`
  built its `Recorder::Spec` with `inputB = -1`. That made a mono take of the left side, and `ClipSource`
  then played it down both sides for good.
- The audio graph was stale in the same way.

**Changed:**

- `AssignPage::commit()` updates the DAW at once.
- `DawEngine::startRecording` starts from the controller's own assignments, so a take always records what the
  mixer shows.
- Leaving the routing workspace reconfigures a stale graph.

**Representation: one 2-channel WAV per stereo take**, as the Recorder already wrote one. The reasons:

- The WAV header and its one sidecar are repaired as one unit after a crash.
- The file is the raw device channels exactly as they arrived.
- `AudioClip` and `ClipSource` already read a 2-channel file as L and R.
- Two linked mono files would have meant two sidecars and two headers that must agree.

The sidecar now stores `inputA` and `inputB`, so a crashed take goes back onto the pair it recorded even after
the inputs are rearranged. Sidecars written before this change still recover by track index.

**Found, not changed:** the width stage's "mono below" high-passes the side signal with no matching phase on
the mid. A left-only 330 Hz tone therefore reaches the right side at about -11 dB per stage, and it stacks
across the channel, the group and the master. At 2 kHz the image is clean (L 1992 against R 240 through the
whole mix). This is existing DSP behaviour guarded by `tests/reference`; changing it needs listening, not a
quiet edit.

## 3. Export looked frozen

**Root cause.** `MixBounce` already rendered on a worker and reported progress once per 1024 samples.
`MainView::exportMix` passed an empty callback, and the only feedback was a toast that lasted five seconds.
Other gaps:

- Quitting mid-export destroyed `HostServices` under the worker.
- There was no way to stop an export.
- The loudness pass and the MP3 encode reported nothing.

**Changed:**

- `ExportProgress` (`app/native/ExportProgress.h`) holds atomics that the worker writes and the 30 Hz tick
  reads.
- `MixBounce::Stage`: Mixing, Loudness and Finishing report progress; Encoding reports none but can still be
  stopped.
- **The status foot.** The second cell (the one a narrow window keeps) reads "Export mixing 42%", "making the
  MP3", "done" or "failed". The seam over the foot becomes an accent bar, or a sweep when the stage has no
  number. Clicking the cell does what fits:
  - while it runs: offers "Stop the export";
  - when done: shows the file in Finder;
  - when it failed: says why again.
- 100% is never shown while the worker is still inside the render. "done" is set only after every writer has
  closed and the file has been moved into place.
- One export at a time, as before.
- Quitting asks, then stops the export and waits for the worker. Files that were half made are deleted.

## 4. Cmd+Z reset the session

**Root cause.**

- Cmd+Z (and Cmd+Shift+Z) was command 200 on **every** workspace: `TracksPage::undo()`.
- That undo replaced the whole `Project` with a stored copy. The stack was never cleared or remapped across a
  new or opened session, a track move, an import that made tracks, or a take.
- One undo could therefore put back a timeline from before the take that had just been recorded. It could
  also put clips under other inputs after a reorder, or bring back the previous session's folder and markers.
  All of that was then autosaved.
- On MIXER, TUNE and LIVE the change was invisible.
- In the mix history itself:
  - `setStripChannel` pushed a whole-mix snapshot on every call, so one knob turn filled the 64-entry history.
  - A fader move was never an entry, so Cmd+Z after a fader move would have undone whatever came before it.

**Changed. Two undo domains, never one snapshot:**

- **The mix.**
  - Hand edits are one entry per gesture: fader, pan, trim, mute, send, effects, chain knobs and the group and
    effects-return levels. The same control within 1.5 s is the same gesture (`markHandEdit`).
  - Labels name the channel, for example "Lead fader".
  - The history now holds 128 entries.
  - Autopilot's own moves are not hand edits.
- **The timeline.**
  - An entry is the clips and markers only. It never holds the folder, the rate, arming, monitoring or LIVE
    SAFE.
  - An entry applies only in the `DawEngine` timeline epoch it was made in. The epoch moves on a session
    opened, new or imported, a re-layout, a take landing, or a recovered take.
  - Redo exists.
  - Undo is refused while recording.
- **Cmd+Z by workspace.**
  - On TRACKS it undoes whichever domain was touched last.
  - Everywhere else it undoes the mix.
- **Cmd+Shift+Z** is redo, and follows the undo it reverses.
- Edit > Undo and Edit > Redo name what they would do.

**Not undoable, by design:** devices, permission, reconnects, the record files, record start and stop,
DIM and MUTE, autosave.

## 5. Drum kits

**Existing library.**

- `SampleBankTable::kSounds` is 24 per family. It was 8, raised on 2026-09-28, and the overflow is said out
  loud.
- The shipped, licensed sounds (Splice certificate in `app/Samples`) are 3 kicks, 4 snares and 4 toms. The
  toms are sizes of one kit, not characters.
- With so few sounds the cap is not the constraint, and a kit names sounds, never slots, so the cap was left
  alone.

**Added: `app/native/DrumKits`.**

- Four kits, made only from shipped sounds:

  | Kit | Kick | Snare |
  | --- | --- | --- |
  | Church | Perfect kick | Church snare |
  | Punchy | Punch kick | Powerful snare |
  | Soft | Soft kick | Crisp snare |
  | Big | Perfect kick | Exploder snare |

  All four share the toms: 10, 12 and 13 inch racks in strip order, and the 16 inch floor tom.
- Applying a kit sets `replaceSound` on each kick, snare and tom strip as **one** mix-history entry. Whether
  the stage is on, its blend, sensitivity, alignment and everything TUNE fitted are untouched. LIVE SAFE holds
  a kit change.
- **The kit is never stored.** It is read off the strips' own `SampleChoice`s, which are already saved by name,
  so a hand-picked snare, an undo, or an old session all report it correctly. When no kit matches, it reads
  "Custom".
- **No session version change.**
- **UI:** a "Drum kit: Church" picker in the Inspector's Sample stage, beside Sound, HEAR IT and Import.

**Still needed:** more licensed one-shots before more kits mean anything. The names Modern, Live, Warm and
Studio were not used, because no shipped sound fits them.

## 6. Broadcast readiness, cleaned up (the same day, second pass)

What was wrong, beyond the look:
- The sheet threw away and rebuilt every row and button 30 times a second (`refresh()` called `rebuild()`
  unconditionally), so a click could land on a button that no longer existed.
- Rows had a fixed height, so guidance that wrapped ran into the next section.
- Editing a past record copied it over `active`, and the service in progress was lost.
- A finished service still looked editable, and silently refused every click.
- Answers were a click anywhere on the row, cycling through four states that were never shown. A note was a
  hidden Shift-click; a name was a hidden double-click.
- "Checked" was drawn green, against the no-green rule.
- Observations:
  - Inputs nobody had measured were counted as "healthy".
  - The favourite check counted automatic checkpoints, not favourites.
- A permanent 32 pt band on MIXER pushed the console down on every broadcast session. Its button read
  "Open · 1/15", and its `panelOpen` state was saved into the session.
- The sidebar row used the same icon as Scenes.
- The shortcuts destroyed the sheet from inside its own button callback.

Now:
- `BroadcastReadinessSheet` is rebuilt to the v3 sheet pattern:
  - a header line saying where things stand, with the close mark;
  - List Rows of lamp, what, why, DINE's observation and the note;
  - Done / Problem / Skip on a segment track (pressing the lit answer again takes it back);
  - Add a note only on a problem;
  - the footer: Start over, then Finish. Once finished: Reopen, then Start the next service.
- The service name and Checked by are fields at the top.
- Past services lists each finished service: when, by whom, how far it got and what was wrong. Open shows a
  service read-only, and "Correct it" edits that record in place.
- The list is rebuilt only when what it shows changes. The observations update in place on the existing rows.
- Model:
  - `setReadinessItem` works on any record.
  - `reopenActive` is new.
  - A blank checklist is never archived.
  - `panelOpen` is removed (the format was never released).
  - Item text is shorter and plain.
  - Statuses read To do / Done / Problem / Skipped.
- The MIXER band is gone. The sidebar row has its own icon (Check) and shows "4/15" once a checklist has
  started.

Tests:
- `BroadcastReadinessTests`: three new cases.
  - Correcting a past service leaves the active one alone.
  - A finished service is read-only until it is reopened, and Finish replaces its history entry rather than
    duplicating it.
  - No input is called healthy until it has been measured.
- `dine_ui_tests`:
  - The sheet opens and Escape closes it.
  - Thirty ticks with nothing changed rebuild nothing.
- Snapshots: `18d-broadcast-readiness`, `18e-broadcast-readiness-finished` and
  `18f-broadcast-readiness-past`. The text-clipping report is empty.

## 7. A sample sounds different on HEAR IT than on the drum

Both paths decode the same file identically: the mono sum, the trim and the rate are all the same. The
differences come after a hit:

1. **The attack was skipped.** A hit is recognised 1.6 to 4.5 ms late, and the player started that far into
   the sample to line it up with the microphone. That went past the snare's crack (its peak is about 1 ms
   in) and the kick's beater click: 1.4 to 3.8 dB of peak and top end lost on every triggered hit.
   - Now the skip stops half a millisecond before the hit's own peak, found by a bounded scan of its first
     20 ms (`SamplePlayer::trigger`).
   - At a blend of 0.9 or more nothing is skipped, because with no microphone left there is nothing to comb
     against.
2. **A stolen voice stopped dead.** The scope document says a 2 ms fade; the code had none. Stolen voices
   now fade out on their own tail slots.
3. **HEAR IT ignored Pitch and "Follows the drum"**, and capped Level at 0 dB where the channel allows
   +12 dB. It now plays at the strip's own rate and level (`MixController::auditionSample`).

Intended, and now said in HEAR IT's tooltip: on the channel the sample is blended with the microphone at its
velocity, and goes through the drum's processing. HEAR IT plays it on its own.

`livemix_tests`: 239 cases, 0 failed, including two new `SamplePlayer` cases (the attack is kept; a steal
fades). The reference renders are unchanged.
