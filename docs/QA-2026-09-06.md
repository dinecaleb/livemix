## Bugs (fix before commit)

### B1. `livemix_ui_snapshots` aborts at exit: `std::system_error: mutex lock failed: Invalid argument`
Every run finishes writing all PNGs and then terminates with an uncaught exception (SIGABRT, non-zero
exit). `EINVAL` from `mutex::lock` means a mutex was used after its owner was destroyed, i.e. an
object-lifetime / static-destruction-order problem in the processor/editor teardown path. Because the
tool builds the real `DrumsProcessor` + `DrumsEditor`, this needs to be shown to be a harness-only
issue before shipping; a host removing the plugin follows the same destructor path.
See "Backtrace" at the bottom of this file.

### B2. Dangling reference: `ParamTile::getParamId()` (`src/UI/Widgets.h:84`)
```cpp
const juce::String& getParamId() const { return spec.id; }   // spec.id is std::string
```
Returns a reference to a temporary `juce::String` (11× `-Wreturn-stack-address`). Currently unused, so
it does no harm yet, but it is undefined behaviour the moment someone calls it. Return by value.

### B3. Disk I/O and XML parsing on the UI timer, 60× per second
`DrumsEditor::refreshShell()` calls `drums.aiProviderAvailable()` every tick (60 Hz). That goes
`OpenAIProvider::isAvailable()` → `AISettings::load()` → `getFile()` (`createDirectory()` + stat) →
`XmlDocument::parse(File)` → `getEnvironmentVariable()`. So every open editor performs a directory
create, a file read and an XML parse 60 times a second on the message thread. `getAnalyzeButtonText()`,
`getAIProviderName()` and the settings menu do the same. Cache the settings in memory (load once, reload
after Save) and make `isAvailable()` read the cache.

### B4. AI request cannot be cancelled; message thread can block for up to the AI timeout
`OpenAIProvider::interpret()` polls `shouldCancel` only before and after the blocking `post()`, and the
HTTP call has no cancellation hook. In `AnalyzeCoordinator` the worker does
`std::async(...)`; `future.wait_for(timeout)`; on timeout the comment says "we no longer wait for it", but
the `std::future` returned by `std::async` **blocks in its destructor** until the task finishes, so the
worker thread stays alive until the HTTP call returns. Consequences:
- `AnalyzeCoordinator::run()` (next Analyze) and `~AnalyzeCoordinator` (plugin removal / host quit) call
  `joinWorker()` and block the message thread for up to `timeoutSeconds` (default 60 s, max 300 s).
- The coordinator timeout is effectively a no-op, because the JUCE connection timeout is set to the
  same value.
This was harmless with the fake providers in the tests; with a real network provider it is a UI hang.
Options: give the provider a way to abort the stream (keep the `WebInputStream` and call `cancel()`),
or detach the helper and let the coordinator drop the result by generation (it already checks
`generation`).

### B5. `static bool lastLiveSafe` in `DrumsEditor::refreshShell()` is shared across instances
With two editors open where one has Live Safe on and the other off, each timer tick sees a mismatch,
flips the static, and calls `resized()`: both editors re-layout 60 times a second, and the Live-Safe
banner height can be wrong. Make it a member.

### B6. `KitPanel::Row` keeps a raw `IKitEndpoint*` copied at construction
`refreshCapture()` dereferences it on every `setResult()` call, which runs every tick while the kit is
in the `Analyzing` state. `InstanceRegistry::unregisterInstance` removes the entry but cannot clear the
copy in the row; the row list is only rebuilt every 30 ticks. Deleting a member instance while a kit
analysis is running is a use-after-free window of up to 0.5 s. Look the endpoint up by id through the
registry at call time instead of caching the pointer.

### B7. `DrumsProcessor::testAIConnection` detaches a thread
The detached `std::thread` captures a `std::function` and posts back with `MessageManager::callAsync`.
The `SafePointer` guards the editor, but nothing guards the plugin binary: if the host unloads the
component while the 20 s test request is in flight, the thread returns into unmapped code. Use a joinable
thread owned by the processor (or `juce::Thread` / `ThreadPool`) and join in the destructor.

## Backtrace for B1 (root cause found)

```
thread #1, stop reason = signal SIGABRT
  std::terminate()
  __clang_call_terminate
  juce::CoreTextTypeface::~CoreTextTypeface() + 580
  livemix::LiveMixLookAndFeel::typefaceFor(int, int)::Cache::~Cache() + 56
  __cxa_finalize_ranges  /  exit
```

`LiveMixLookAndFeel::typefaceFor()` keeps the nine embedded typefaces in a function-local
`static Cache` (`src/UI/LiveMixLookAndFeel.cpp`, `typefaceFor`). That static is destroyed at `exit()`,
after `ScopedJuceInitialiser_GUI` has already run `shutdownJuce_GUI()`, so `~CoreTextTypeface` locks a
mutex that no longer exists and the runtime terminates. In the AU the same destructor runs when the
host unloads the component, after JUCE's shutdown, so this is a plugin-unload / host-quit crash risk,
not just a tool nit. Fix: make the cache non-static (a member of `LiveMixLookAndFeel`, one per editor,
cheap because `Typeface::Ptr` is ref-counted), or hold it in a `juce::SharedResourcePointer` /
`DeletedAtShutdown` object so it dies before JUCE does.
